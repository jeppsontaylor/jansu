## Phase 07 target

**Phase 07 is not “just make Produce return `NONE`.”** The phase doc requires exact non-transactional Produce behavior before idempotence and transactions are claimed: valid/invalid acks, partition/topic validation, CRC/magic/timestamp/compression validation, size checks, per-partition error mapping, no mutation before validation failure, `acks=0` wire silence, and Java/librdkafka proof before advertisement. The audit also keeps Produce unadvertised until stable client/differential proof exists.  

Current repo state is a strong partial implementation: API key 0 is routed, `ProduceService` validates acks and several batch invariants, broker tests prove `acks=0` suppression and v0..v11 decode, and the ledger explicitly marks Produce as routed but unadvertised/partial.   

One big compatibility gap needs to be called out: the repo ledger says local Produce descriptors max at v11, but Kafka 4.2 documents Produce v12 and v13; v13 switches request/response topic identity from topic name to topic ID. For a “100% Kafka replacement” target, Phase 07 must either update `jansu-sans-io` to Kafka 4.2 Produce v13 or explicitly cap advertisement to v11 and record that as a compatibility limitation. I would update to v13. ([Apache Kafka][1])

A second critical scope issue: Kafka 4.2 producer defaults enable idempotence, require `acks=all`, and default `acks` to `all`; Phase 07 explicitly leaves idempotent producer semantics to Phase 11. So Phase 07 can be closed only as **normal non-idempotent Produce exactness** unless Phase 11’s idempotent state machine is pulled forward. ([Apache Kafka][2])

## Final Phase 07 definition of done

Phase 07 is done when all of these are true:

1. **Protocol coverage**

   * `ProduceRequest` and `ProduceResponse` schemas support Kafka 4.2 Produce v0..v13.
   * If v12/v13 are not added, the ledger must say “compatible only through v11,” and `ApiVersions` must advertise only v0..v11.
   * Response shape is version-correct: v5+ has `log_start_offset`, v8+ has record errors/error message, v10+ has tagged current-leader/node-endpoints, and v13 uses `topic_id`.

2. **Broker advertisement**

   * `jansu_broker::service::advertised_versions()` advertises Produce only after differential/client proof is checked into the ledger.
   * The compatibility contract continues to enforce that advertised versions exactly match ledger-approved versions. The current contract already requires approved/current advertised versions to match. 

3. **Non-idempotent Produce semantics**

   * `acks` accepts only `0`, `1`, and `-1`.
   * `acks=0` appends if possible but sends no wire response.
   * `acks=1` responds after leader-local append.
   * `acks=-1` behaves as `acks=all`; in the current single-node/no-replica model, this is success only when the topic’s effective ISR/min-ISR policy is satisfied.
   * Idempotent/transactional batches are rejected truthfully unless Phase 11/12 state is present and certified.

4. **Validation before append**

   * Topic/partition exists.
   * Caller is authorized, or the configured auth layer is explicitly allow-all.
   * Request/batch/message limits are enforced.
   * Record batch magic, CRC, batch length, offset deltas, record count, timestamps, and compression are validated before append.
   * Supported producer compression matrix includes `none`, `gzip`, `snappy`, `lz4`, and `zstd`; Kafka producer docs list those valid compression values. ([Apache Kafka][2])
   * Unsupported compression or malformed compressed payloads fail without append.

5. **Per-partition exactness**

   * One bad partition must not poison unrelated partitions in the same request.
   * One bad batch in a partition prevents append for that partition.
   * All successful partition offsets are contiguous and stable.

6. **Storage mutation safety**

   * Schema validation failures must not advance offsets, watermarks, producer state, or lake-sink state.
   * DynoStore’s lake-sink branch must move schema validation before watermark mutation; today that branch increments watermark before schema validation, which violates the Phase 07 requirement. 

7. **Client proof**

   * Java producer proof and librdkafka proof are checked in.
   * Differential Kafka proof compares Jansu responses to Kafka 4.2 for success and failure cases.
   * The ledger row for API key 0 points to those tests and records the exact advertised range/scope.

Batch validation should be a pure function. It must not call storage and must not mutate anything:

```rust
fn validate_batch_exact(
    batch: &deflated::Batch,
    limits: &ProduceLimits,
) -> Result<ValidatedBatch, ErrorCode> {
    let attributes = BatchAttribute::try_from(batch.attributes)
        .map_err(|_| ErrorCode::UnsupportedCompressionType)?;

    if batch.magic != 2 {
        return Err(ErrorCode::InvalidRecord);
    }

    if batch.base_timestamp < 0
        || batch.max_timestamp < 0
        || batch.max_timestamp < batch.base_timestamp
    {
        return Err(ErrorCode::InvalidTimestamp);
    }

    let encoded = Bytes::from(batch.clone());
    if encoded.len() > limits.max_message_bytes {
        return Err(ErrorCode::MessageTooLarge);
    }
    if encoded.len() > limits.max_record_batch_bytes {
        return Err(ErrorCode::RecordListTooLarge);
    }

    let inflated = inflated::Batch::try_from(batch)
        .map_err(|_| ErrorCode::CorruptMessage)?;

    if inflated.records.is_empty() {
        return Err(ErrorCode::InvalidRecord);
    }

    let actual_count = i32::try_from(inflated.records.len())
        .map_err(|_| ErrorCode::CorruptMessage)?;

    if actual_count != batch.records_count {
        return Err(ErrorCode::CorruptMessage);
    }

    let expected_last_delta = actual_count - 1;
    if batch.last_offset_delta != expected_last_delta {
        return Err(ErrorCode::CorruptMessage);
    }

    // Keep the current canonical re-encode CRC/batch_length check.
    let canonical = deflated::Frame {
        batches: vec![inflated.clone()],
    };

    let canonical = deflated::Frame::try_from(canonical)
        .map_err(|_| ErrorCode::CorruptMessage)?;

    let Some(canonical_batch) = canonical.batches.first() else {
        return Err(ErrorCode::CorruptMessage);
    };

    if canonical_batch.batch_length != batch.batch_length || canonical_batch.crc != batch.crc {
        return Err(ErrorCode::CorruptMessage);
    }

    Ok(ValidatedBatch {
        batch: batch.clone(),
        record_count: actual_count,
        encoded_bytes: encoded.len(),
        first_timestamp_ms: batch.base_timestamp,
        max_timestamp_ms: batch.max_timestamp,
        attributes,
    })
}
```

The exact enum names may need adjustment to whatever `jansu_sans_io::ErrorCode` generated, but the Kafka error classes must be preserved: `INVALID_REQUIRED_ACKS`, `UNKNOWN_TOPIC_OR_PARTITION`, `UNKNOWN_TOPIC_ID`, `TOPIC_AUTHORIZATION_FAILED`, `CORRUPT_MESSAGE`, `INVALID_RECORD`, `INVALID_TIMESTAMP`, `UNSUPPORTED_COMPRESSION_TYPE`, `MESSAGE_TOO_LARGE`, `RECORD_LIST_TOO_LARGE`, `NOT_ENOUGH_REPLICAS`, and `NOT_ENOUGH_REPLICAS_AFTER_APPEND`. Kafka 4.2’s protocol table defines these relevant error codes and meanings. ([Apache Kafka][1])

Partition handling should follow this order:

```rust
async fn produce_partition<S>(
    storage: &S,
    transaction_id: Option<&str>,
    topic: &ResolvedTopic,
    partition: &PartitionProduceData,
    request_acks: i16,
    limits: &ProduceLimits,
) -> PartitionProduceResponse
where
    S: Storage + ?Sized,
{
    let index = partition.index;
    let topition = Topition::new(topic.name(), index);

    if !topic.has_partition(index) {
        return partition_error(index, ErrorCode::UnknownTopicOrPartition);
    }

    let Some(records) = partition.records.as_ref() else {
        return partition_error(index, ErrorCode::InvalidRecord);
    };

    let mut validated = Vec::with_capacity(records.batches.len());

    for batch in &records.batches {
        if batch.is_idempotent() && !storage.capabilities().supports(StorageFeature::ProducerState) {
            return partition_error(index, ErrorCode::UnknownProducerId);
        }

        match validate_batch_exact(batch, limits) {
            Ok(batch) => validated.push(batch),
            Err(error_code) => return partition_error(index, error_code),
        }
    }

    if request_acks == -1 {
        if let Err(error_code) = topic.check_min_isr_for_acks_all() {
            return partition_error(index, error_code);
        }
    }

    let mut base_offset = None;

    for batch in validated {
        match storage.produce(transaction_id, &topition, batch.batch).await {
            Ok(offset) => {
                base_offset.get_or_insert(offset);
            }
            Err(err) => {
                return partition_error(index, map_storage_error(err));
            }
        }
    }

    let stage = storage.offset_stage(&topition).await.ok();

    PartitionProduceResponse::default()
        .index(index)
        .error_code(ErrorCode::None.into())
        .base_offset(base_offset.unwrap_or(-1))
        .log_append_time_ms(-1)
        .log_start_offset(stage.map_or(0, |stage| stage.log_start()))
        .record_errors(Some(vec![]))
        .error_message(None)
}
```

Storage errors must be mapped deliberately, not collapsed:

```rust
fn map_storage_error(error: Error) -> ErrorCode {
    match error {
        Error::Api(code) => code,
        Error::Schema(_) => ErrorCode::InvalidRecord,
        Error::SegmentMissing { .. } | Error::SegmentEmpty(_) => ErrorCode::KafkaStorageError,
        Error::UnsupportedStorageUrl(_) => ErrorCode::KafkaStorageError,
        _ => ErrorCode::UnknownServerError,
    }
}
```

### 8. Fix DynoStore lake-sink mutation ordering

The current DynoStore lake-sink branch calculates and persists watermark before schema validation. That can advance offsets when schema validation fails, directly violating Phase 07’s no-mutation-before-final-failure rule. 

Patch shape:

```rust
async fn produce(
    &self,
    transaction_id: Option<&str>,
    topition: &Topition,
    deflated: deflated::Batch,
) -> Result<i64> {
    let config = self
        .describe_config(topition.topic(), ConfigResource::Topic, None)
        .await?;

    let attributes = BatchAttribute::try_from(deflated.attributes)?;

    let inflated_for_validation = if !attributes.control
        && (self.schemas.is_some() || self.lake.is_some())
    {
        Some(inflated::Batch::try_from(&deflated)?)
    } else {
        None
    };

    if let (Some(registry), Some(inflated)) = (&self.schemas, &inflated_for_validation) {
        registry.validate(topition.topic(), inflated).await?;
    }

    // Only after all pure validation passes:
    let offset = self.allocate_and_persist_offset(topition, &deflated).await?;

    // Lake storage happens after the Kafka log append decision. If lake sink is mandatory,
    // make offset/watermark commit the last durable write or compensate on failure.
    if !attributes.control
        && let (Some(lake), Some(inflated)) = (&self.lake, &inflated_for_validation)
    {
        lake.store(
            topition.topic(),
            topition.partition(),
            offset,
            inflated,
            config,
        )
        .await?;
    }

    Ok(offset)
}
```

### 9. Implement exact `acks=all` policy for current single-node storage

Kafka defines `acks=0`, `acks=1`, and `acks=all`; `acks=all` is equivalent to `acks=-1` and waits for the in-sync replica set. ([Apache Kafka][2])

Current tests treat `Ack::FullIsr` as a successful storage path or a wire response path, but there is no real ISR/min-ISR decision.  

Add a minimal policy object:

```rust
#[derive(Clone, Debug)]
struct IsrStatus {
    leader_id: i32,
    replica_count: usize,
    isr_count: usize,
    min_insync_replicas: usize,
}

impl IsrStatus {
    fn validate_acks_all_before_append(&self) -> Result<(), ErrorCode> {
        if self.isr_count < self.min_insync_replicas {
            Err(ErrorCode::NotEnoughReplicas)
        } else {
            Ok(())
        }
    }
}
```

For current single-node Jansu topics:

* `replication_factor=1`
* `isr_count=1`
* `min.insync.replicas=1`
* `acks=-1` succeeds after durable local append

Do not use `replication_factor=0` in Phase 07 compatibility tests; Kafka topics are not meaningfully compatible with zero replicas.
